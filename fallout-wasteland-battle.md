# Fallout: Битва за Пустошь

> Реактивная многопользовательская стратегия с захватом территорий на карте вселенной Fallout.

Игроки (до 4 человек) управляют фракциями, перемещают отряды между ключевыми локациями, атакуют и укрепляют точки. Визуализация — наложение маркеров на реальное изображение карты. Действия обрабатываются мгновенно через WebSocket, состояние хранится в Redis, все события логируются через Kafka для репликации и анализа.

---

## 1. Суть проекта

- **Игровой мир** — статический граф узлов (локации: Убежище 101, Мегатонна, Башня Тенапенни и т.д.) с координатами для наложения на фоновую картинку.
- **Игроки** — до 4 человек в одной сессии. Каждый начинает с 1–2 стартовыми базами и небольшим гарнизоном.
- **Механика** — клик по узлу открывает контекстное меню: атаковать соседнюю точку, переместить юниты, укрепить оборону.
- **Мгновенность** — каждое действие применяется сразу (без раундов), конфликты разрешаются атомарными Lua-скриптами в Redis.
- **Взаимодействие** — через WebSocket (STOMP или raw) для отправки команд и получения обновлений в реальном времени.
- **Масштабируемость** — события передаются через Kafka, позволяя горизонтально масштабировать обработку команд и рассылку уведомлений.

Проект демонстрирует навыки реактивного программирования, распределённых систем, работы с Redis как in-memory state store и построения event-driven архитектуры.

## 3. Архитектура микросервисов

Проект разбит на 4 основных микросервиса + 2 вспомогательных инфраструктурных компонента.

### 3.1. Схема взаимодействия

```
[Frontend (браузер)]
        │ WebSocket (STOMP)
        ▼
[API Gateway] (Spring Cloud Gateway)
        │
        ├─► регистрация в Eureka
        │
        ├─► REST: /lobby/** → Lobby Service
        ├─► WebSocket: /ws/** → Gateway & Broadcaster Service
        │
        └─► маршрутизация запросов к другим сервисам через Discovery
```

**Поток команд:**

1. Клиент → WebSocket → Gateway Broadcaster → Kafka topic `game-commands`
2. Game Engine (Consumer) ← Kafka → выполняет Lua-скрипт в Redis → отправляет событие в `game-events`
3. Gateway Broadcaster (Consumer) ← Kafka → рассылает дельты через WebSocket клиентам

### 3.2. Сервисы

| Сервис | Порт | Описание |
|---|---|---|
| Service Discovery (Eureka Server) | 8761 | Регистрирует все микросервисы, обеспечивает их обнаружение. |
| API Gateway | 8080 | Единая точка входа. Проксирует REST-запросы и WebSocket-соединения. Выполняет аутентификацию (JWT) при необходимости. |
| Lobby Service | 8081 | Управление игровыми сессиями: создание, подключение игроков, старт игры. Генерирует начальное состояние и записывает его в Redis. Отправляет событие `SESSION_STARTED` в Kafka. Использует PostgreSQL для хранения метаданных сессий. |
| Game Engine Service | 8082 | Ядро игры. Реактивный Kafka Consumer (`game-commands`). Выполняет Lua-скрипты в Redis. Публикует события результата в `game-events`. Не имеет собственной БД, вся логика основана на Redis и сообщениях. Горизонтально масштабируется (партиционирование по `sessionId`). |
| Gateway & Broadcaster Service | 8090 | Управляет WebSocket-сессиями (`ReactiveWebSocketHandler`). Хранит маппинг `sessionId → активные сессии`. Consumer для `game-events` — получает события и отправляет их соответствующим клиентам через WebSocket. |
| History Service | 8083 | *(Опционально)* Слушает `game-events`, сохраняет историю ходов в PostgreSQL для реплеев и статистики. Предоставляет REST API для просмотра завершённых игр. |

### 3.3. Взаимодействие через Kafka

- **`game-commands`** — команды от игроков (ключ = `sessionId` для гарантии порядка в партиции).
- **`game-events`** — события изменения состояния игры (ключ = `sessionId`).
- **`lobby-events`** — события создания/закрытия сессий.

Все сервисы подписываются на нужные топики через `@KafkaListener` (реактивный или с использованием `ReactiveKafkaConsumerTemplate`).

### 3.4. Структура данных в Redis

Префикс ключей: `game:{sessionId}:`

| Ключ | Тип | Содержимое |
|---|---|---|
| `meta` | Hash | `{ "status": "IN_PROGRESS", "turn": 0, "startedAt": "..." }` |
| `player:{playerId}` | Hash | `{ "name": "...", "resources": 100, "totalUnits": 20 }` |
| `node:{nodeId}` | Hash | `{ "owner": null\|playerId, "garrison": 10, "fortification": 0 }` |
| `edges` | Set | Строки вида `"nodeA:nodeB"` (для проверки смежности) |
| `static:nodes` | Hash | Координаты и названия (загружается при старте сервиса) |

### 3.5. API (примеры)

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/lobby/create` | Создать новую сессию, вернуть `sessionId` и `joinCode`. |
| `POST` | `/lobby/join?code=...&playerName=...` | Подключиться к сессии по коду. |
| `GET` | `/lobby/session/{sessionId}/state` | Получить полное состояние игры (для первоначальной загрузки). |
| `WebSocket` | `/ws/game/{sessionId}/{playerId}` | Подключение к игровому каналу. Формат сообщений: JSON с полем `action` (`attack`, `move`, `reinforce`) и параметрами. |

## 4. План разработки по спринтам

> Длительность спринта: 2 недели (всего 6 спринтов = 3 месяца).
> Если вы работаете в свободное время — корректируйте сроки под себя.

### Спринт 0: Подготовка инфраструктуры *(1–2 дня)*

- Настройка проекта: многомодульный Gradle/Maven, общие зависимости (`spring-boot-starter-webflux`, `spring-kafka`, `lettuce`, `eureka-client`).
- Подготовка `docker-compose.yml` с контейнерами: PostgreSQL, Redis, Kafka (с Zookeeper), Eureka Server.
- Создание базового Spring Boot приложения для Eureka Server.

### Спринт 1: Ядро игровой логики + Redis *(без сети)*

**Цель:** реализовать чистую Java-логику игры и проверить её через Redis без WebSocket и Kafka.

- Разработать доменные модели: `Player`, `Node`, `GameState`, `Order`.
- Написать Lua-скрипты для Redis:
  - `attack.lua` — атомарная атака на соседний узел.
  - `move.lua` — перемещение юнитов между своими узлами.
  - `reinforce.lua` — укрепление узла.
- Создать `RedisGameRepository` с использованием Lettuce (реактивный клиент).
- Написать JUnit/Testcontainers тесты, симулирующие одновременные запросы от 4 потоков.
- Разработать консольный (или простой Web) симулятор для ручного тестирования.

**Результат:** Работающее ядро с атомарными операциями, покрытое тестами.

### Спринт 2: Lobby Service + REST API

**Цель:** создать управление сессиями и предоставить REST API для создания/подключения.

- Реализовать `LobbyService` со Spring WebFlux.
- Настроить PostgreSQL (или H2 для тестов) для хранения сессий.
- Создать эндпоинты:
  - `POST /lobby/create` — генерирует уникальный код.
  - `POST /lobby/join` — добавляет игрока; при достижении 4 отправляет событие в Kafka (`SESSION_STARTED`).
- При старте игры инициализировать Redis: записать статическую карту и начальное состояние для каждого игрока.
- Интегрировать Eureka (зарегистрировать сервис).

**Результат:** Можно создавать комнаты и подключаться через Postman.

### Спринт 3: WebSocket + Gateway Broadcaster *(без Kafka)*

**Цель:** реализовать WebSocket-связь и мгновенную отправку обновлений без Kafka (для упрощения отладки).

- Создать `GatewayBroadcasterService` с `WebSocketHandler`.
- Реализовать `SessionManager` для хранения активных WebSocket-сессий.
- Пока команды обрабатываются синхронно: WebSocket → вызов `RedisGameRepository` → ответ клиенту.
- Написать простой HTML-клиент (JS WebSocket), который отрисовывает карту (Canvas) и отправляет команды.
- Интеграция с Eureka.

**Результат:** Можно играть вдвоём с одного компьютера (разные вкладки) через WebSocket, видя мгновенные изменения.

### Спринт 4: Внедрение Kafka, разделение на Engine и Broadcaster

**Цель:** перевести общение между сервисами на событийную модель.

- Вынести обработку команд в отдельный `GameEngineService`.
- Настроить Kafka (топики `game-commands`, `game-events`).
- WebSocket-сервис отправляет команды в `game-commands` (продюсер).
- Engine слушает `game-commands`, выполняет Lua-скрипты и публикует события в `game-events`.
- Broadcaster слушает `game-events` и рассылает их через WebSocket.
- Добавить обработку ошибок и Acknowledgement для гарантированной доставки.
- Протестировать локально с 2 экземплярами Engine (партиционирование).

**Результат:** Полностью реактивная, событийная архитектура. Возможность горизонтального масштабирования.

### Спринт 5: API Gateway + Security (JWT) + Frontend polishing

**Цель:** добавить внешний шлюз, защиту и улучшить клиентскую часть.

- Настроить Spring Cloud Gateway с маршрутами к сервисам (через Eureka).
- Реализовать простую аутентификацию (JWT) при создании/подключении к сессии (опционально).
- Доработать фронтенд:
  - Загрузка реальной картинки Fallout.
  - Наложение маркеров узлов (из статического API).
  - Контекстное меню по клику.
  - Отображение состояния (владелец, гарнизон).
  - Поддержка переподключения (reconnect).
- Добавить таймауты для неактивных игроков (автоматический пропуск ходов).

**Результат:** Играбельный прототип с красивым UI и удобным управлением.

### Спринт 6: История, мониторинг, полировка и деплой

**Цель:** завершающие штрихи для production-ready версии.

- Реализовать `HistoryService`, сохраняющий все события в PostgreSQL для реплеев.
- Добавить эндпоинт `GET /history/{sessionId}` для просмотра завершённой игры.
- Настроить метрики (Micrometer) и дашборды в Grafana (опционально).
- Написать интеграционные тесты с Testcontainers (Kafka, Redis, Postgres).
- Оптимизировать Lua-скрипты, настроить Redis persistence (RDB/AOF).
- Упаковать всё в Docker Compose для одного-командного запуска.
- Создать документацию по развёртыванию.

**Результат:** Готовый продукт, который можно показать в портфолио или развернуть на облачной платформе.

## 5. Советы по разработке

- **Начинайте с чистого ядра** — не подключайте сеть и БД, пока не отработаете логику и атомарность Redis. Используйте встроенный Redis (Testcontainers) для юнит-тестов.
- **Используйте реактивные обёртки осторожно** — для простоты можно начать с обычных `@KafkaListener` и блокирующих вызовов, а затем перейти к реактивным (`ReactiveKafkaConsumerTemplate`, `Mono`/`Flux`).
- **Держите Lua-скрипты в отдельных файлах** (`src/main/resources/lua/`), загружайте их при старте и используйте SHA для эффективного вызова.
- **Партиционирование в Kafka** — всегда указывайте ключ = `sessionId` при отправке команд и событий. Это гарантирует, что все события одной игры попадут в одну партицию и будут обрабатываться последовательно.
- **Обрабатывайте отключения клиентов** — при закрытии WebSocket отправляйте событие `PLAYER_DISCONNECTED` в Kafka, чтобы Engine мог переключить игрока в режим AFK.
- **Валидация команд** — проверяйте все входные данные на стороне Engine (не только на фронте), чтобы избежать читерства.
- **Тестируйте нагрузку** — используйте `wrk` или JMeter для симуляции нескольких игроков, отправляющих команды одновременно, чтобы убедиться в корректности атомарных операций.
- **Используйте Docker Compose для локальной разработки** — это избавит от проблем с установкой Redis/Kafka и позволит быстро перезапускать сервисы.
- **Ведите логирование всех событий** — это поможет отлаживать рассинхроны. Используйте MDC для передачи `sessionId` в каждый лог.
- **Не бойтесь упрощать** — если какой-то микросервис кажется избыточным (например, History), объедините его с другим на первых порах. Главное — начать и получать удовольствие от процесса!
