# Проектирование схемы PostgreSQL с Liquibase

Скилл для проектирования DDL PostgreSQL и оформления его в виде Liquibase changelog'ов (YAML),
с автоматическим применением списка анти-паттернов PostgreSQL из
[wiki.postgresql.org/Don't_Do_This](https://wiki.postgresql.org/wiki/Don't_Do_This).

## Когда использовать

- Пользователь просит спроектировать таблицу(ы) или всю схему БД
- Пользователь просит написать/сгенерировать Liquibase changelog или changeSet
- Пользователь просит добавить миграцию (новая колонка, индекс, constraint, FK)
- Пользователь просит проверить существующий DDL или changelog на плохие практики

## Рабочий процесс

### 1. Уточнить контекст, если он не дан
Не переспрашивай, если пользователь и так дал достаточно контекста (например, "таблица orders:
id, покупатель, сумма, статус, дата создания" — этого достаточно, чтобы начать). Спрашивай только,
если реально не хватает данных для DDL: какие сущности/поля нужны, какие связи (FK), нужны ли
уникальные/составные индексы, ожидаемый объём данных (влияет на выбор индексов и партиционирование).

### 2. Спроектировать DDL, применяя чеклист анти-паттернов
Перед тем как писать финальный DDL, прогони каждое поле и объект через
`references/dont-do-this.md`. Это происходит "по умолчанию" и не обсуждается с пользователем —
пользователь не должен получить `char(10)`, `serial` или `varchar(255) на всякий случай`, если для
этого нет явной причины из чеклиста ("когда правило можно нарушить").

Ключевые дефолты, которые скилл применяет автоматически (подробности и обоснования — в
`references/dont-do-this.md`):
- `timestamptz` вместо `timestamp` для любых моментов времени, без precision `(0)`
- `text` вместо `char(n)`/`varchar(n) "на всякий случай"` (лимит через `CHECK`, если реально нужен)
- `numeric` вместо `money`
- identity-колонка (`GENERATED ALWAYS AS IDENTITY`) вместо `serial`/`bigserial`
- `snake_case` для всех имён таблиц/колонок, без заглавных букв
- никакого `CREATE RULE` и table inheritance для моделирования сущностей (только партиционирование)
- если в changeSet попадает SQL с `NOT IN (SELECT...)` или `BETWEEN` по датам — переписать на
  `NOT EXISTS` / явные `>= ... AND < ...`

### 3. Оформить как Liquibase YAML changelog
Используй структуру и соглашения из `assets/changeset-template.yaml` (один changeSet, все типы
constraint'ов, rollback) и `assets/master-changelog-example.yaml` (структура master-файла и
соглашение об именовании файлов). Правила:
- один changeSet = одно логическое изменение (создание таблицы, отдельно — индекс, отдельно — FK,
  если FK добавляется к уже существующей таблице)
- `id` changeSet'а = имя файла без расширения: `<YYYY-MM-DD>-<порядковый номер>-<kebab-case описание>`
- у каждого changeSet с `createTable`/`addColumn`/`dropColumn`/`addCheckConstraint` и т.п. — обязательно
  блок `rollback`
- для потенциально опасных операций (`dropColumn`, `dropTable`, `renameColumn`) добавляй
  `preConditions` с проверкой существования объекта

### 4. Объяснить пользователю только реально важные решения
Не пересказывай весь чеклист. После DDL коротко перечисли (2–5 пунктов) те решения, которые
пользователь мог бы принять иначе, и почему выбран именно такой вариант — например: "id — identity,
а не serial", "created_at — timestamptz", "статус — text + CHECK, а не enum/varchar". Если
пользователь прислал существующий DDL/changelog на ревью — перечисли конкретные найденные
нарушения чеклиста с указанием, что и на что заменить.

## Файлы скилла

- `references/dont-do-this.md` — полный чеклист анти-паттернов с обоснованием и исключениями.
  Читай его перед проектированием DDL, не пытайся вспомнить правила по памяти.
- `assets/changeset-template.yaml` — эталонная структура одного changeSet'а (таблица, PK, FK,
  numeric, check constraint, rollback).
- `assets/master-changelog-example.yaml` — структура master changelog'а и соглашение об именовании
  файлов миграций.

## Что скилл не делает

- Не выбирает движок/хостинг БД, не пишет docker-compose (если это отдельно не попросили)
- Не заменяет ревью человеком для миграций с большими таблицами в проде (dropColumn, изменение типа
  колонки на больших таблицах) — для таких случаев явно предупреждай о блокировках и необходимости
  `pg_repack`/online-миграции, но не проектируй саму стратегию нулевого даунтайма без отдельного запроса
