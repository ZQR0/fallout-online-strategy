# Чеклист анти-паттернов PostgreSQL

Источник: https://wiki.postgresql.org/wiki/Don't_Do_This

Формат каждого пункта: **что не делать** → **что делать вместо этого** → почему → когда правило можно нарушить.
Используй этот файл как справочник при проектировании схемы и написании changeSet'ов. Не обязательно
пересказывать пользователю каждый пункт — применяй их молча в DDL и объясняй только те решения,
которые реально повлияли на конкретную таблицу/колонку.

## Типы данных

### timestamp → timestamptz
Не используй `timestamp` (без часового пояса) для хранения моментов времени. Используй `timestamptz`.
`timestamptz` хранит точку во времени в UTC и корректно работает с арифметикой между разными
часовыми поясами и переходами на летнее/зимнее время. `timestamp` — это просто "картинка календаря",
без информации о том, в каком поясе она была записана.
Исключение: если это абстрактные дата-время без арифметики (например, просто читаете и пишете как есть)
или нужна обратная совместимость с БД без нормальной поддержки часовых поясов.
В Liquibase: `type: TIMESTAMPTZ` (не `TIMESTAMP`), не храните UTC-время в `timestamp without time zone`.

### timetz и CURRENT_TIME
Никогда не используй `timetz` и функцию `CURRENT_TIME` — они существуют только для соответствия
стандарту SQL и почти всегда дают не то, что ожидается. Вместо этого: `CURRENT_TIMESTAMP`/`now()`
для `timestamptz`, `LOCALTIMESTAMP` для `timestamp`, `CURRENT_DATE` для `date`, `LOCALTIME` для `time`.

### timestamp(0) / timestamptz(0)
Не указывай precision (особенно 0) для timestamp-колонок — это округляет, а не отбрасывает дробную
часть, из-за чего сохранённое значение может оказаться на полсекунды в будущем. Если нужна точность
до секунды — используй `date_trunc('second', ...)`.

### char(n)
Не используй `char(n)`, даже для полей фиксированной длины (коды стран, хеши, ID из внешних систем).
`char(n)` дополняет значение пробелами и не проверяет минимальную длину — то есть не даёт вообще
никакого преимущества перед `text`. Используй `text` с ограничением `CHECK (length(col) = n)` или
`CHECK (col ~ '^...$')` — это одновременно и лаконичнее, и надёжнее.

### varchar(n) "по умолчанию"
Не ставь `varchar(n)` автоматически "на всякий случай". По производительности и месту на диске
`varchar(n)`, `varchar` и `text` идентичны. Если нужен реальный лимит длины — `varchar(n)` подходит,
но если лимит взят "с потолка" (типа `varchar(255)` для фамилии) — используй `text`, а для более
сложных ограничений — `CHECK` constraint.

### money
Не используй тип `money` для денежных сумм. Используй `numeric` (плюс отдельную колонку с валютой,
если нужно). `money` завязан на локаль `lc_monetary` сервера, не хранит валюту вместе со значением
и плохо ведёт себя при смене этой локали.

### serial
Для новых таблиц не используй `serial`/`bigserial`. Используй identity-колонки:
`GENERATED ALWAYS AS IDENTITY` (или `GENERATED BY DEFAULT AS IDENTITY`, если нужно иногда вставлять
явное значение). `serial` создаёт менее прозрачную связь между таблицей и последовательностью
(проблемы с правами, зависимостями, переносом схемы).
В Liquibase (YAML) это выражается через `generationType: ALWAYS` в `<column>`/`identity`, а не
через `type: SERIAL`.

## Именование

### UPPER/CamelCase имена
Не называй таблицы и колонки `ЛюдиКлиенты`, `OrderID` и т.п. PostgreSQL приводит все не-квотированные
идентификаторы к нижнему регистру, поэтому смешанный регистр вынуждает либо всегда квотировать имя,
либо никогда — а разные инструменты (включая сам Liquibase) делают это по-разному, что приводит к
ошибкам "relation does not exist". Используй только `a-z`, `0-9` и `_`: `snake_case`.
Если нужны "красивые" имена в отчётах — используй алиасы (`select foo as "Foo Name"`), а не имена
колонок.

## SQL-конструкции (актуально для представлений, функций, генерируемых колонок в changeSet'ах)

### NOT IN
Не используй `NOT IN (SELECT ...)` — при NULL в подзапросе результат непредсказуемо (и обычно
неверно) даёт 0 строк, а план выполнения на больших данных может деградировать до O(N²).
Используй `NOT EXISTS (SELECT ... WHERE ...)`. `NOT IN (константы,...)` без подзапроса — можно, если
точно известно, что списке нет NULL.

### BETWEEN с датами/таймстампами
Не используй `BETWEEN` для диапазонов timestamp — это включает обе границы, и запрос
`BETWEEN '2018-06-01' AND '2018-06-08'` захватит `2018-06-08 00:00:00`, но не более поздние моменты
того же дня. Пиши явно: `col >= '2018-06-01' AND col < '2018-06-08'`. Для дискретных величин
(integer, date) `BETWEEN` безопасен.

## Работа с БД на уровне объектов

### RULE
Не используй `CREATE RULE`. Правила переписывают запрос ещё до выполнения и почти никогда не ведут
себя так, как ожидается для нетривиальных случаев. Если нужна условная логика на INSERT/UPDATE/DELETE —
используй триггер (`CREATE TRIGGER` + функция на PL/pgSQL).

### Наследование таблиц
Не используй `table inheritance` для моделирования связей "родитель-потомок" в духе ООП — эта идея
не оправдала себя на практике. Для родственных задач сейчас есть нативное партиционирование
(`PARTITION BY`) — используй его. Для связей между сущностями — внешние ключи.

## Аутентификация / доступ (важно при генерации connection-конфигов, docker-compose, pg_hba.conf)

### trust-аутентификация по TCP/IP
Никогда не разрешай `trust`-аутентификацию (`host ... trust`) по сети в проде — это позволяет
подключиться от имени любого пользователя, включая суперпользователя. Используй
`scram-sha-256` (доступно с PostgreSQL 10+). `trust` допустим только для localhost в dev/CI-окружении.

### SQL_ASCII
Не создавай базу с кодировкой `SQL_ASCII` — она означает "без конвертации", и со временем в такой БД
накапливается нечитаемая смесь кодировок. Используй `UTF8`.

## Быстрый чеклист перед тем как отдать DDL/changeSet пользователю

- [ ] Все timestamp-колонки — `timestamptz`, без `(0)` precision
- [ ] Нет `char(n)` — только `text` (+ `CHECK`, если нужна фиксированная длина)
* [ ] Нет `varchar(n)` "на всякий случай" без реального смысла в лимите
- [ ] Денежные суммы — `numeric`, не `money`
- [ ] Автоинкрементные PK — identity-колонка, не `serial`
- [ ] Все имена таблиц/колонок — `snake_case`, без заглавных букв и без нужды в квотировании
- [ ] Нет `RULE`, нет table inheritance (кроме партиционирования)
- [ ] Если есть SQL с `NOT IN (SELECT...)` — заменено на `NOT EXISTS`
- [ ] Если есть `BETWEEN` по timestamp — заменено на `>= ... AND < ...`
- [ ] Кодировка БД — `UTF8`, не `SQL_ASCII`
- [ ] Если генерируется конфиг доступа — нет `trust` по TCP/IP в проде
